# QA-EVIDENCE-MIDNIGHT-AGAIN

Cause: the seven Blender recipes that plan `.evidence/<day>/` (test-fighter, crew-fighters, first-person-gear, rustwall, scrapdome-yard, scablands-boneyard, p4-kits) each read Python's `date.today()` on their own clock, outside the one-clock cure of 19 November. The test read the clock again for each child process, so a run across midnight (or any machine whose date differed from the fixed one) planned two days. Case 4 compared the browser's day with Blender's and failed at 00:35 on 20 November.
Fix: `tools/blender/evidence_date.py` is the Python twin of `tools/evidence-date.mjs` and reads `DUEL_EVIDENCE_NOW` too; six recipes import it, `p4-kits.py` carries the same few lines inline because its planning audit allows it to read nothing but itself. `evidenceClockText()` writes one moment as that value. Case 4 reads the clock once and hands every child that moment.
New test: "Blender, browser and round planner name one folder across midnight with an older day folder present" sets the clock at 23:59:59, 00:00:00, 00:01 and 00:35 with 18 and 19 November folders present, for all four Blender recipes, the browser runner and the round planner, and checks a bad clock is refused. Negative control: against the old recipes it fails (test-fighter planned the real date, 2026-11-26).
